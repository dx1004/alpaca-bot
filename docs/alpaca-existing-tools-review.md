# Reuse existing Alpaca tooling

Reviewed 2026-10-03. Decision for development planning: use the [official `alpaca-py` SDK](https://github.com/alpacahq/alpaca-py) as the preferred Alpaca API transport/model layer **after** a pinned, offline compatibility and paper-only adapter check. Do not build duplicate account, historical-data, WebSocket or order HTTP clients just because the original plan listed modules. The reviewed [v0.44.0 release](https://github.com/alpacahq/alpaca-py/releases/tag/v0.44.0) is a candidate, not yet installed or accepted in this repository. No dependency, credentials, account state, trading path or subscription changed during this review.

| Project work | Existing component to evaluate | Project-owned acceptance boundary |
| --- | --- | --- |
| W1-05 read-only capability probe | [`TradingClient`](https://alpaca.markets/sdks/python/api_reference/trading/trading-client.html) for account, assets, clock/calendar; historical-data and stream clients for entitlement checks | Keep the already tested redacted probe until SDK parity is demonstrated. Report response status/field presence without values, require paper credentials, and reject live endpoints. An SDK constructor is not proof of an entitlement. |
| W2-03/W2-04 market data | [`StockHistoricalDataClient`](https://alpaca.markets/sdks/python/api_reference/data/stock/historical.html) for bars/trades/quotes and [`StockDataStream`](https://alpaca.markets/sdks/python/api_reference/data/stock/live.html) for live trades/quotes/bars/status/corrections | Persist raw source and first-seen times, detect gaps and corrections, bound backfill, label IEX versus SIP eligibility, and replay without future data. SDK reconnect/re-subscription does not by itself prove uninterrupted coverage. |
| W2-06 news | Official [news REST/stream clients](https://github.com/alpacahq/alpaca-py/tree/v0.44.0/alpaca/data) | Preserve original story/version and availability, deduplicate/revise, map tickers, and apply only sourced Ross catalyst rules. SDK delivery does not establish source freshness, completeness or strategy meaning. |
| W3-04/W3-05 paper execution | [`TradingClient` order/account methods](https://alpaca.markets/sdks/python/api_reference/trading/orders.html) and [`TradingStream`](https://alpaca.markets/sdks/python/api_reference/trading/stream.html) trade updates | Persist intent and unique client ID **before** submission; reconcile ambiguous responses through REST and stream, including partial fills, cancel races and restart. The [documented order lifecycle](https://docs.alpaca.markets/us/docs/orders-at-alpaca#order-lifecycle) has nonterminal states. |

The [SDK trading constructor](https://alpaca.markets/sdks/python/api_reference/trading/trading-client.html) exposes `paper=True` **and** live mode and URL override. Instantiate it only behind the repository's exact paper-host validation, explicit paper flag and separate paper credentials. Its released v0.44.0 [market stream](https://github.com/alpacahq/alpaca-py/blob/v0.44.0/alpaca/data/live/websocket.py) and [trade stream](https://github.com/alpacahq/alpaca-py/blob/v0.44.0/alpaca/trading/stream.py) include reconnect work; data-silence timeout is opt-in in that released source. Reconnection still needs local gap detection and recovery evidence. The inspected [REST source](https://github.com/alpacahq/alpaca-py/blob/v0.44.0/alpaca/common/rest.py) does not establish a bounded request timeout for every call, so the adapter must verify timeout/retry behavior before replacing the existing probe or using an order path.

The older [`alpaca-trade-api-python` repository](https://github.com/alpacahq/alpaca-trade-api-python) is archived. Alpaca's [momentum example](https://github.com/alpacahq/Momentum-Trading-Example) describes a different 45-minute/Python 3.6/Polygon setup and is not a Ross strategy baseline. Broader frameworks such as [LumiBot's Alpaca integration](https://lumibot.lumiwealth.com/backtesting.alpaca.html) or [LEAN's Alpaca brokerage](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/brokerages/alpaca) are optional comparison candidates, not adopted runtime dependencies: their data, order, safety, cost and replay semantics have not passed this project's gates. No verified ready-made Ross bot was found in the bounded official-source review; this does not prove none exists.

Next implementation check: pin one tested `alpaca-py` version under Python 3.12 in the project-local lock, verify offline imports/typed models, then run fake-transport paper/live rejection and read-only parity tests. Only after securely configured paper credentials are available should W1-05 compare actual account/data entitlements. W2/W3 may then use the SDK for API plumbing while retaining deterministic Ross rules, eligibility vetoes, durable journal and reconciliation. No API call that submits or cancels an order is part of this review.
